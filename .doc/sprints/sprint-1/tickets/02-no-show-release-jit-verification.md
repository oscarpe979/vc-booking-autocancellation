# 02: No-Show Release Workflow & Just-In-Time Release Validation

**What to build:** An unoccupied room with an active, eligible scheduled booking automatically initiates a no-show release countdown. Rapid availability events are coalesced with a 50ms buffer, and missing metadata triggers a 5-step bounded recovery sequence. A countdown starts only when the remaining meeting time is strictly greater than the release horizon and the device uptime can be read as the workflow's reboot baseline. At the pre-timeout warning threshold (`PRE_TIMEOUT_WARNING_MS`), the warning deadline is fixed, an actionable warning is requested (ticket 03), and a warning email is dispatched to the organizer under the email gate rules owned by ticket 10. At the deadline, the service runs the full Just-In-Time (JIT) release validation checklist (LLD §5.5). If every check passes, a checkout request releases the room and a cancellation notice is sent to the organizer. Any failed check aborts the release and preserves the booking.

**Blocked by:** 01: Core Scaffolding & End-to-End Tracer Bullet, 10: Corporate SMTP Email Notification Engine & Template System

**Status:** ready-for-agent

- [ ] Rapid bursts of availability status and timestamp events are coalesced with a 50ms timer (`bookingSyncCoalesceDelayMs`) before fetching booking details (LLD §5.2)
- [ ] If transient booking metadata is missing or unavailable, a 5-step bounded readiness recovery schedule ([250ms, 500ms, 1000ms, 2000ms, 4000ms]) executes; each attempt rebuilds the full snapshot using `getBookingDetails` (`Bookings.Get({ Id })`) for a known ID or `getCurrentBooking` (`Bookings.List({ ScheduleType: 'Current', Limit: 1 })`) when the ID is missing, and exhaustion preserves the booking (LLD §5.3)
- [ ] Minimum remaining time is a countdown-start check: a countdown starts only when `timeRemaining` is strictly greater than the release horizon (`EMPTY_ROOM_TIMEOUT_MS + POST_TIMEOUT_GRACE_PERIOD_MS` in `LIVE`, `EMPTY_ROOM_TIMEOUT_MS` in `DRY_RUN`); otherwise the skip is logged (`Ns remaining; requires >Ms`) and the booking expires naturally
- [ ] When a room is confirmed empty at the start of an eligible booking with no CheckIn confirmation, a no-show countdown of `EMPTY_ROOM_TIMEOUT_MS - PRE_TIMEOUT_WARNING_MS` starts with a new `releaseWorkflowId`
- [ ] Every countdown start reads `getUptimeSeconds()` and stores `deviceUptimeBaselineSeconds` and `workflowStartedAt` (LLD §5.13); an unreadable uptime starts no countdown and preserves the booking
- [ ] *Pending device test DT1* (LLD §5.9): if DT1 shows the CheckIn state is readable, a No-Show countdown also requires a fresh `getCheckInState()` reporting `NotCheckedIn`; `CheckedIn` records CheckIn confirmation (no countdown, prompt, or email; Early Departure applies if enabled), and an unreadable state starts no countdown. If DT1 is negative, this criterion and JIT check 12 are removed and the residual gap in LLD §5.9 applies (the warning email wording is owned by ticket 10)
- [ ] When the countdown fires, the warning deadline (`promptExpiresAt`) is fixed once: `PRE_TIMEOUT_WARNING_MS + POST_TIMEOUT_GRACE_PERIOD_MS` in `LIVE`, `PRE_TIMEOUT_WARNING_MS` in `DRY_RUN`. It is never extended by a chime-tick controller re-read or re-display (ticket 03), dismissal restoration, or the confirmation guard
- [ ] At the warning point, the service requests the warning prompt through the interaction driver (ticket 03) and dispatches the warning email for this deadline (gate rules in ticket 10, LLD §5.8)
- [ ] Fleet gates (kill switch, tripwire; LLD §5.8) are evaluated before every countdown start, warning, and CheckOut; when either is active the action is not taken (fleet-gate effects are owned by ticket 11)
- [ ] At the deadline, the service runs every check of LLD §5.5 in order; prompts are cleared only for the checks marked in §5.5. This includes:
  - check 5 (`LIVE` only): a fresh `readPromptSurfaces()` that is readable (not failed, not `403`), shows at least one controller, and returns exactly the `controllerIdsAtDisplay` set while the workflow still holds controller ownership; or an interactive OSD owns the displayed prompt. Otherwise `no_actionable_prompt_surface` (ownership rules in ticket 03);
  - service-only gate 9: fleet gates clear, warning email covered the current deadline or `NOTIFICATIONS_ENABLED=false`, `warningEmailFailed` not set, room mode `LIVE` or `DRY_RUN`;
  - service-only gate 10: VIP/keyword re-evaluation against fresh booking details;
  - service-only check 11: a fresh `getUptimeSeconds()` is readable, not lower than `deviceUptimeBaselineSeconds`, and not less than the workflow's age; failures are `device_rebooted_during_workflow` or `device_uptime_unavailable`, and a detected reboot restarts the actor with startup semantics (ticket 05);
  - check 12, *pending device test DT1*, No-Show policy only: a fresh `getCheckInState()` reports `NotCheckedIn`; `CheckedIn` aborts with `booking_checked_in` and records CheckIn confirmation, and an unreadable state aborts with `checkin_state_unavailable`. Removed if DT1 is negative
- [ ] A `PresenceChanged(Unknown)` or a failed presence read while a booking is active and not quarantined cancels automatic CheckIn and the release workflow, clears prompts, and sets `Blocked / RoomUseStatusUnavailable` until full presence revalidation succeeds
- [ ] If every check passes in `LIVE`, the service marks the pending service CheckOut before calling `checkOut(roomId, bookingId, 'NoShow')`, then clears prompts
- [ ] A `checkOut()` rejection in the same lifecycle clears the pending service CheckOut and sets `Blocked / CheckOutFailed` for the rest of the lifecycle; the service never calls `Delete`; a stale failure from an older lifecycle changes nothing
- [ ] Upon successful calendar release, a cancellation notice email (No-Show template) is dispatched to the meeting organizer via the notification driver
- [ ] In `DRY_RUN`, the countdown fires into `PromptPending`: the service logs `[DRY RUN - WOULD_DISPLAY_PROMPT]` and `[DRY RUN - WOULD_SEND_EMAIL]` (which satisfies the email gate), arms the deadline with no grace, runs the JIT checklist without the actionable-surface check (check 5), and logs `[DRY RUN - WOULD_RELEASE]` instead of sending a CheckOut, displaying a prompt, playing audio, or sending a real email
- [ ] Automated tests verify the complete no-show release lifecycle in `LIVE` and `DRY_RUN`, the countdown-start horizon per mode, the uptime baseline (an unreadable uptime starts no countdown), bounded readiness recovery, warning email gating, `RoomUseStatusUnavailable`, `CheckOutFailed`, and Just-In-Time safety aborts using virtualized clocks, including check 5 with a changed controller set and with a `403` read, check 11 with a lower uptime and with an unreadable uptime, and, if DT1 is positive, the countdown-start CheckIn state read and check 12
