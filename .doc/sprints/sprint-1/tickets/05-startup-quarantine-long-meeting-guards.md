# 05: Startup Quarantine, Booking Policy & Lifecycle Guards

**What to build:** Enterprise meetings are protected against improper cancellation during service maintenance, system reboots, mode promotions, and prolonged or VIP sessions. Any meeting already active when a room's actor is created is quarantined until the meeting ends: no CheckIn event is ever delivered to Workspace Integrations (LLD §5.9), so there is no release signal. Meetings longer than two hours, organized by designated VIPs, matching exempt title keywords, or with unverifiable calendar data are blocked from autocancellation. The identity-bound autocancellation status owns the native CheckIn setting (LLD §5.6). The service also handles lifecycle transitions (meeting end, rollover, end-time change), schedules the codec-local midnight health check, which re-applies the room's configuration before it re-verifies (LLD §5.12), detects device reboots from `SystemUnit.Uptime` (LLD §5.13), and observes external releases.

- [ ] While the coalescing buffer and classification run, the status is `Blocked / VerifyingMeetingLength` with no native CheckIn write
- [ ] Any current booking whose verified duration exceeds the configured threshold (e.g. 120 minutes) is classified as `LongMeeting`; a booking organized by a configured VIP or containing an exempt title keyword is `ExemptOrganizerOrTitle`; a booking whose start/end times or identity cannot be verified is `Unclassifiable`. Each is blocked for the rest of the lifecycle with no automatic check-in, countdown, prompt, or checkout
- [ ] Native CheckIn ownership (LLD §5.6) in `LIVE`: `Allowed` writes `True`; `VerifyingMeetingLength` writes nothing; any other `Blocked` reason (including `AwaitingStartupCheckIn`) writes `False`; no current booking writes `True`. A CheckOut is only issued for an `Allowed` booking whose `True` write has applied. A failed enable records `NativeCheckInSettingUnavailable`; a failed disable keeps the reason and is retried by readiness recovery
- [ ] In `DRY_RUN`, actor start and every re-apply (midnight, recovery, reconnect, lease re-acquire) read `Bookings.CheckIn.Enabled` and write `False` only when it is enabled (failing closed if unreadable or unwritable); the service never enables native CheckIn in `DRY_RUN`. In `LIVE`, a re-apply re-runs the native CheckIn policy for the current status and never writes `Enabled` blindly. `MONITOR_ONLY` makes no native write. Fleet gates never change a booking status, and no native CheckIn write is made while one is active
- [ ] Availability becoming `Free` or `FreeUntil` starts a new lifecycle: all timers are cancelled, prompts are cleared, and native CheckIn is set to `True` (`LIVE` only). A `FreeUntil` timestamp is the next booking start and is never used as a current end
- [ ] If a known booking ended before its scheduled end and was not the service's own pending CheckOut, the service emits an `[EXTERNAL_RELEASE_OBSERVED]` structured audit log
- [ ] A change of the current booking ID (rollover) cancels old timers and prompts, resets per-lifecycle CheckIn and email state, and evaluates the new booking as first observed after actor creation (no quarantine)
- [ ] A booking end-time change during a countdown or prompt triggers fresh classification; a long or unclassifiable result clears prompts, cancels timers, invalidates the workflow, sets native CheckIn `False` (`LIVE`), and logs the suspension
- [ ] The service parses the codec-local timezone offset from `getCodecTime()` (`Time.SystemTime`) to schedule the codec-local midnight health check; if invalid or unavailable, it flags `CodecTimeUnavailable` and suspends release
- [ ] Each room's midnight health check runs at codec-local midnight plus a per-room random delay of up to `MIDNIGHT_HEALTH_CHECK_JITTER_MAX_MS` (15 minutes), so the fleet does not hit Webex rate limits at once
- [ ] The midnight health check first applies the room mode's configuration writes (LLD §5.12), batched with `setMany` where possible, then re-verifies configuration, presence, booking snapshot, and codec time. `DRY_RUN` and `LIVE`: `RoomAnalytics.PeoplePresenceDetector=On`, `PeoplePresence.Input.HeadDetector=On`, `PeopleCountOutOfCall=On`, `PeoplePresence.Input.Ultrasound` per `ultrasoundSensorEnabled` (`Off` by default), `RoomInUse.InCall=Enabled`, `RoomInUse.LocalUsage=Enabled`, and `Bookings.CheckIn.WindowDuration` from `nativeCheckInWindowMinutes`; then `Enabled=False` (`DRY_RUN`) or the native CheckIn policy (`LIVE`). `MONITOR_ONLY` and `DISABLED`: no writes. While the kill switch or tripwire is active, the presence and window writes still run and native CheckIn writes are skipped
- [ ] Bounded readiness recovery attempts, an ingress reconnect, and a lease re-acquire run the same writes-then-revalidate order (LLD §5.3, §5.12)
- [ ] The midnight health check keeps an active valid workflow without duplicating timers and reschedules itself; a failed write or validation cancels the workflow and prompts, preserves the booking, sets the matching transient block (`RequiredConfigurationsUnavailable` or `NativeCheckInSettingUnavailable`), and hands over to readiness recovery
- [ ] Device reboot detection (LLD §5.13): `getUptimeSeconds()` is read when a countdown starts (baseline), on each 60-second chime tick, and at JIT check 11. When the uptime is lower than the baseline or less than the workflow's age, the service aborts with `device_rebooted_during_workflow`, cancels the workflow, clears prompts, preserves the booking, and restarts the actor with startup semantics: an in-progress meeting is quarantined until it ends (`Enabled=False` in `LIVE`), followed by the full reconciliation above
- [ ] A `BootEvent` (`Restart`, `Shutdown`, `Upgrade`) is only an early trigger: the actor cancels any workflow, clears prompts on a best-effort basis, restores volume, preserves the booking, and sets `deviceReconcilePending`; the next event or read runs the uptime check and full reconciliation. It never authorizes or gates a release, and a missed `BootEvent` is still caught by the uptime reads
- [ ] Automated tests verify quarantine at startup and on promotion holding an empty meeting safe until it ends, long/VIP/keyword/unclassifiable classification, native CheckIn writes per status and mode, meeting end, rollover, end-time change, external release observation, midnight success and failure, the midnight writes per mode (none for `MONITOR_ONLY`; presence and window only while a fleet gate is active), per-room jitter, reboot detection (lower uptime and uptime less than the workflow age both quarantine the in-progress meeting), and a `BootEvent` cancelling the workflow without releasing
