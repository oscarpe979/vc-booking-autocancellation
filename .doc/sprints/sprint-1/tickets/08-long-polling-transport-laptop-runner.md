# 08: Outbound Long-Polling Ingress Transport & Local Laptop Runner

**What to build:** An engineer working on a corporate laptop can boot the entire service with a single command (`npm run dev`) and connect to the organization's Webex cloud queue via outbound long-polling. The service receives live telemetry and interaction events from physical test rooms without opening any inbound firewall ports or running third-party tunnels, routing events through the roster gate to the matching room actors and coordinating the full autocancellation lifecycle. The entrypoint also starts the local admin dashboard.

**Blocked by:** 03: In-Room User Interaction (Audio Chimes, Prompts & Check Out), 04: Occupancy Interruption & Automatic Check-In, 05: Startup Quarantine, Booking Policy & Lifecycle Guards, 06: Early Departure Release Policy, 07: Webex Workspace Integration Driver Adapter, 09: Lightweight Admin Dashboard & Configuration UI, 10: Corporate SMTP Email Notification Engine & Template System, 11: Fleet Roster, Room Enrollment & Durable Configuration Store

**Status:** ready-for-agent

- [ ] `LongPollingTransport` implements `IEventIngressTransport`; long polling starts automatically inside the SDK's `connect({ notifications: 'longpolling' })`, and the transport never calls the SDK's internal polling function directly
- [ ] Telemetry, interaction, and `BootEvent` events arriving on the long-poll connection pass the roster gate and are dispatched to the corresponding room actor in the registry; events from devices that are not enrolled are discarded before dispatch
- [ ] Poll errors and recovery are reported through `onConnectivityChange`; on reconnection after an outage, every actor re-applies its mode's configuration writes and then runs a full revalidation (LLD §7.2, §5.12, and the readiness reconciliation of §5.3) before any new countdown may start
- [ ] The entrypoint (`src/index.ts`) first starts the dashboard listener with `GET /healthz`, so a store or lease wait is reported as `STORE_UNAVAILABLE` / `LEASE_NOT_HELD`; it then loads the fleet configuration store (with the startup retry behaviour of ticket 11), runs inventory reconciliation, acquires the instance lease, registers actors only for enrolled (non-`DISABLED`, `Present`) rooms, opens the roster gate, then initializes the transport and begins monitoring
- [ ] The entrypoint starts the admin dashboard (ticket 09) bound to 127.0.0.1 and refuses to start when `ADMIN_DASHBOARD_PASSWORD` is not configured
- [ ] The service executes on a corporate development machine behind proxies and firewalls with zero inbound ports and no database server (admin state lives in the local JSON file store)
- [ ] `GET /healthz` follows LLD §7.3: exact-match route registered before the auth, session, CSRF, and rate-limit middleware; answered from in-memory state only; `detail` from fixed templates with no personal data; `200 ok` with no issues, `200 degraded` with only warnings, `503 unhealthy` with any critical issue. It raises and clears `STORE_UNAVAILABLE`, `STORE_DEGRADED`, `LEASE_NOT_HELD`, `WEBEX_DISCONNECTED`, `EVENT_LOOP_STALLED`, `TRIPWIRE_TRIPPED`, `EMAIL_DELIVERY_FAILING`, and `KILL_SWITCH_ACTIVE`, backed by the transport's `ingressDisconnectedSince` and the notification adapter's `consecutiveSmtpFailures`. If the listener cannot bind or `ADMIN_DASHBOARD_PASSWORD` is missing, the process exits non-zero before opening the roster gate. The Dynatrace health push and its alert configuration are Sprint 2.
- [ ] Graceful termination closes the roster gate so no further notification is dispatched, tears down every room actor's timers, and exits the process (the SDK cannot stop its polling loop)
- [ ] Automated tests verify end-to-end event routing from incoming long-poll notifications through the roster gate and room actor to outbound mock actions, roster-gate discards, revalidation after a connectivity change, and that `/healthz` raises and clears each issue code with the right status
